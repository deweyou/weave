# Apple 原生界面设计规则

适用于 Weave 的 macOS、iPadOS、iOS 界面设计、实现与走查。本文是基于 Apple 官方资料的项目适配规则，不是 Apple HIG 的全文，也不代表所有条目已实现或验收。核对日期：2026-09-27。

优先级：用户确认的产品范围 → AGENTS / DESIGN / 本规则 → 第三方设计 skill。冲突时先保护数据、稳定输入和可访问性，再考虑视觉。当前产品尺寸和编辑排版的唯一基线在 [DESIGN](../../DESIGN.md)，本文不重复维护数值表。

## 1. 使用边界与来源

- Apple 官方建议用于理解平台行为；下文的“必须”“不得”是 Weave 的执行约束，不应转述成 Apple 对所有 App 的要求。
- 本文统一维护原生视觉与交互规则，动效细节也在本文中，不依赖额外的 Apple 设计 skill。Web 实现示例转译为原生行为约束，不保留 CSS / JavaScript 实现依赖。
- 不直接照搬 CSS、10 px 手势阈值、统一弹簧参数、放大模糊/阴影等示例。原生组件优先使用系统反馈、手势识别与材质。
- 按下时给反馈，操作按原生控件的提交规则执行；“立即反馈”不等于按下就执行删除等操作。
- 不把“所有小字都加字距”“所有大字都减字距”“所有导航都铺玻璃”当作通则。字体、背景和动画应按实际场景核查。
- 使用新 API 前查本机 SDK 声明和官方 availability；官网出现新接口不表示当前部署版本已支持。Web 示例或后续系统能力不能改变原生技术路线。

### 设计决策的八项检查

下列原则用作项目设计评审的问题，不作为增加功能的授权：

| 原则 | 评审问题 |
| --- | --- |
| 目的 | 这个元素解决什么实际任务，是否值得占用注意力？ |
| 自主 | 用户能否控制、打断、取消和撤销，选择是否被强迫？ |
| 责任 | 是否保护内容和隐私，权限是否在需要时解释并请求？ |
| 熟悉 | 同样的语义是否沿用平台位置、外观与行为，例外是否有证据？ |
| 灵活 | 不同窗口、输入方式、能力和语言是否仍可完成任务？ |
| 简单 | 常见操作是否直接，复杂选项是否渐进呈现，而非全部隐藏？ |
| 工艺 | 边距、基线、状态、性能是否一致且可解释？ |
| 愉悦 | 安静、可预期和顺手是否来自整体质量，而非额外装饰？ |

同时检查安全感、可理解性、完成任务的成就感与使用愉悦。参考：[Principles of great design](https://developer.apple.com/videos/play/wwdc2026/250/)。

## 2. 内容层、控制层与视觉层级

- 主体是用户内容。导航和操作解释内容，不用大面积装饰、重复卡片或多重边框抢占注意力。
- 优先用对齐、分组、留白、字号与字重建立层级；同一个语义角色保持一致，不能仅靠颜色区分状态。
- Liquid Glass 用于适当的导航和控制层，正文画布保持清楚稳定；不可为追求玻璃效果把文字内容层也改成透明材质。
- 优先使用系统组件的材质和边缘效果。自定义玻璃限于明确需要的功能元素；不重复叠加系统已经提供的模糊、染色、描边与阴影。
- 深度服务于空间关系：普通列表和静态内容不需要浮起；只有遮挡、浮层、拖动等有层级关系的场景才增加相应反馈。
- 模态遮罩表达“父内容暂不可操作”；非模态并行面板不应使用同等遮罩制造阻断错觉。材质上的文字使用适合该材质的语义颜色与 vibrancy，不靠随意加字距弥补对比度。
- 内容滚到浮动控制区下方时优先采用系统 scroll edge 效果；分隔线仍可用于真正的结构边界，不能把“不要自制顶部硬条”误读为禁止所有分隔线。

依据：[Materials](https://developer.apple.com/design/human-interface-guidelines/materials)、[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)。

## 3. 边距、对齐、尺寸与密度

- 先确定对齐对象：容器外沿、文字起点、基线或控件中心。不要在同一层随机混用；图标的视觉中心可以做小幅光学校正，不能破坏点击热区。
- 检查最终累积间距，包含父容器 padding、子视图 padding、原生列表 inset、安全区与滚动容器 inset；禁止各自看似合理但叠加后形成大空档。
- 区分窗口外边距、内容边距、控件内部留白和点击热区。窗口边距小，不代表正文或按钮热区也应该缩小。
- 复用语义化尺寸，不为凑网格机械地把所有数值改成 4 或 8 的倍数。系统安全区、字体度量和原生控件尺寸优先；pt 不等于截图物理像素。
- 默认分栏比例应把空间留给主内容。支持的栏宽范围、最小窗口与换行必须一起检查；首次默认值不能在切换笔记或刷新时覆盖用户调整。
- 固定高度只用于有明确平台尺寸的控件；文字、错误说明和翻译内容应允许增长。截断是空间策略，完整内容必须仍能访问。
- 验收既看空页面，也看长标题、多行正文、少量和大量记录；空白并不自动是问题，重复导航和无用途的空栏需要说明价值。

依据：[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)。以上间距管理方法是项目执行规则。

## 4. 同心圆角与容器形状（用户确认）

- 相邻嵌套的圆角表面在靠近同一个外角、具有对应内缩关系时，优先采用同心圆角；目标是让弯曲处与直边处的留白连贯，不是给内外层写相同半径。
- 对真正的圆角矩形、等距内缩 d，几何关系为 `内半径 = max(外半径 − d, 0)`。例如外半径 16 pt、内缩 4 pt，内半径为 12 pt。这个公式用于理解关系，不代替系统对连续曲线、不等距布局的计算。
- SwiftUI 优先使用 `ConcentricRectangle` / `.concentric`，按实际容器传递形状；必要时用 `.containerShape` 明确容器。不要假设所有窗口或所有原生宿主都会自动传递形状。
- 逐角判断。远离窗口外角的左下角、受标题栏影响的顶角、独立笔记卡片，不因“统一”而强制与窗口同心；它们沿用自己的语义圆角。
- 背景、裁剪、描边与命中形状必须兼容；不能圆角背景后还留方形描边，也不能让装饰层截获输入。描边是否向内绘制要明确，不能侵占预定边距。
- 当前 Mac 工作区右、下边距为 4 pt，右下使用同心机制；显式 16 pt 容器轮廓是当前窗口适配值，不是从 NSWindow 动态读取的普适常量。
- 验收包含正常窗口、缩放、全屏/平铺、不同系统版本及有底部状态条的情况。外轮廓变成直角或安全区改变时，检查是否需要调整容器；没有这些证据不能宣称自动适配所有窗口状态。
- 不通过私有 API 读取窗口圆角；优先系统容器信息，缺失时记录公开、有限的适配假设并验证。

依据：[ConcentricRectangle](https://developer.apple.com/documentation/swiftui/concentricrectangle)、[concentric](https://developer.apple.com/documentation/swiftui/edge/corner/style/concentric)。

## 5. 字体、颜色与图标

- UI 采用系统字体与语义文字样式；文档内容遵循自身格式。不要为统一 UI 外观改写用户存储的字号或文字色。
- 层级同时考虑字号、字重、行距和留白，避免多个同等级标题争抢焦点。中英文、数字、emoji 和回退字形都要检查；不能只用拉丁占位文案验收。
- 字体的光学大小、字距和行距与字号、字形及语言有关；优先让系统处理 optical sizing。需要自定义时逐字号检查，大标题的紧凑感和正文的舒展感不可用一套固定 tracking 实现。
- 不对系统字体统一加字距或强制行高；编辑器使用已确认的 `DocumentTypography`，任何度量变动都必须保护选区和插入点。
- 使用语义颜色，强调色承担稳定含义。浅深色不是简单反相；自定义色需覆盖浅色、深色及增加对比度，不能凭“用了系统色”省略实际检查。
- 图标遵守 DESIGN 的 SF Symbols 规则，保持语义、字重和尺度一致；无文字按钮必须有可访问标签，必要时提供帮助提示。
- 不以淡化到不可读来制造“高级感”。次要摘要、日期、禁用原因和分隔线按各自作用判断对比度，不把整页都降为浅灰。

依据：[Fonts](https://developer.apple.com/documentation/technologyoverviews/fonts)、[Color](https://developer.apple.com/design/human-interface-guidelines/color)、[Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)。

## 6. 控件与交互状态

- 优先原生 Button、Toggle、菜单、List 和文本控件。自定义外观必须保留角色、可访问值、焦点和键盘操作，不能只给 Text 加点击手势模拟按钮。
- 对每种交互检查：普通、悬停、按下、选中、键盘焦点、禁用、进行中、失败及窗口失焦。不是每个控件都需新增全部状态，但存在的状态应可辨且不改变布局。
- 热区与可见外观分开设计；触控入口以至少 44×44 pt 作为 Weave 基线，小图标可扩充不可见热区，热区不得互相抢占。Mac 使用适合指针的原生控件尺寸，不把整套 UI 强制扩大到触控密度。
- 手型范围遵循 DESIGN 的用户约定；它是 Weave 规则，不是“Apple 所有控件都必须手型”。正文保留 I 形光标，分隔线保留调整尺寸语义。
- 不把操作只藏在 hover、右键或长按里；必要操作同时提供可发现的菜单、按钮或键盘路径。不能依赖鼠标提示满足触控或 VoiceOver 使用。
- 按钮写清动作。进行中的动作防止重复执行，长任务提供状态和有意义的取消；成功反馈应就近且适量。

依据：[Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)、[Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)。

## 7. 导航、窗口与跨平台适配

- 一眼能够理解当前内容、选中项与返回路径。列表选择、页面标题和编辑对象一致；删除或失效对象要有明确落点。
- macOS 保留窗口控制、可拖动区域、缩放与菜单习惯；隐藏标题栏不等于移除这些能力。装饰覆盖层不能堵住窗口控制或分栏操作。
- 使用可用空间驱动布局。iPad 窗口变窄与 iPhone 不是同一个硬编码设备分支；紧凑布局保留相同对象身份与工作上下文。
- 旋转、键盘出现、分栏收放、窗口缩放或切换内容时，保护编辑记录、输入焦点、选区、滚动位置与未保存内容。
- 多窗口能力只在产品范围内实现；已有窗口的临时菜单、提示、焦点不可错误作用于其他窗口。关闭窗口、退出 App、删除笔记是不同操作。
- 当前 Mac 明确移除的搜索、分类、导入和顶部工具栏，不能因为 HIG 列出这些组件就重新添加。

依据：[Windows](https://developer.apple.com/design/human-interface-guidelines/windows)、[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)。

### 7.1 iOS：紧凑导航与安全区

- 按当前视图可用空间、size class 与字号组织布局，不用设备型号或横竖屏名称决定栏数。支持旋转时同时检查安全区、长标题与大字号，不能只把竖屏等比拉宽。
- 紧凑布局保留清楚的返回路径；`NavigationSplitView` 收拢为导航栈时核对当前选择和显示列，展开后仍是同一记录。不要用重新创建编辑会话来切换布局。
- 正文和必要操作遵守系统安全区、布局边距；背景可以延展，但不能让按钮被传感器、系统栏或屏幕边缘遮挡。不要把 Mac 的 4 pt 窗口外边距移植为手机内容边距。
- 键盘显示、隐藏及交互式收起时，插入点、选区和必要操作保持可达；不写死键盘高度，不重复累加系统已经处理的 inset。

依据：[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[NavigationSplitView](https://developer.apple.com/documentation/swiftui/navigationsplitview)、[Safe area](https://developer.apple.com/documentation/uikit/positioning-content-relative-to-the-safe-area)。编辑会话与 4 pt 的限制是 Weave 项目规则。

### 7.2 iPadOS：窗口、输入与多任务

- 同时考虑全屏与可调整大小的窗口；宽布局可同时呈现侧栏和内容，窄布局收拢层级，不能只针对几种固定分屏比例。缩放过程中的中间宽度也必须可用。
- 保留系统窗口控制和操作空间，不用自制窗口按钮代替；前缘导航或工具栏项目不得与窗口控制重叠。新窗口应有明确任务价值，不因普通导航不断创建窗口。
- 触控、硬件键盘和指针均能完成主要任务；悬停只能增强反馈，不能成为操作的唯一入口。检查焦点、快捷键、文本选择和拖动的竞争关系。
- 对停靠、浮动及未停靠键盘分别检查。UIKit 桥接可用 `UIKeyboardLayoutGuide`，需跟随浮动键盘时评估 `followsUndockedKeyboard`；它不是所有界面都应开启的开关。
- Weave 的编辑保护要求：窗口变窄、失焦或转入后台不能丢失未保存正文、组合输入及当前记录；若后续接入多窗口，每个窗口的导航与临时呈现独立，保存冲突另行设计。规则不表示当前已具备多窗口能力。

依据：[Windows](https://developer.apple.com/design/human-interface-guidelines/windows)、[Elevate the design of your iPad app](https://developer.apple.com/videos/play/wwdc2025/208/)、[Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices)、[键盘布局示例](https://developer.apple.com/documentation/uikit/adjusting-your-layout-with-keyboard-layout-guide)。

### 7.3 折叠形态：官方指导与接入边界

Apple 已提供 iPhone Duo 的专门指导；以下是对这些资料的项目转译，不概括为所有厂商折叠设备的通用 API。

- 用 size class、可用空间和系统安全区适配内外屏及姿态；不为每种姿态维护一套导航。内容、功能与层级保持一致，大屏可增加并列信息。
- 系统栏在适用形态下可移到侧边；布局须接受栏位置及安全区变化，不能把所有操作永久固定在屏幕顶部或底部。
- 必要控件避开折弯区域，优先采用具有系统避让行为的菜单、sheet 和导航组件。连续滚动正文与列表保持连续，不为避折痕强行搬到半屏。

设计依据：[Design for iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111466/)；HIG 入口：[Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)。

- 自定义布局区分分隔区域（division）与遮挡区域（occlusion），根据系统返回的范围和活动状态处理，不写死折痕宽度或相机位置。
- 需要移动时，相关控件成组且就近移动；目的地按内容用途和操作上下文选择。避免为避让破坏触发元素与浮层的关联。
- `ArrangementView` / `UIArrangementViewController` 是布局容器，不能代替导航：主次内容需并列可见时考虑 split，有前景/背景关系时考虑 overlay；避免将导航容器放进 arrangement，或将 arrangement 放进滚动容器。
- Apple 技术讲解明确 arrangements 从 iOS 27.1 提供。接入任何新接口都要逐项核对 SDK 声明和运行时 availability，并保留低版本布局；只有 `#available` 不能解决旧 SDK 不识别符号的问题。

技术依据：[Strike a pose with adaptive layouts on iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111463/)。

Weave 当前状态：这些是设计与验收要求，折叠专用 API 尚未接入、设备交互尚未验收。继续使用现有原生编辑桥接，展开/收拢必须保护记录身份、中文组合输入、UTF-16 选区、撤销、滚动位置及保存；本条是项目编辑器约束。

## 8. 键盘、焦点与原生编辑

- 常见命令沿用系统快捷键和菜单归属；自定义快捷键限于高频动作，不覆盖系统或文本编辑已有语义。
- 检查 Tab / Shift-Tab 焦点顺序、Return 默认动作、Escape 取消、方向键和组合修饰键；焦点可见，不能被透明视图截走。
- 菜单、sheet 或临时浮层关闭后，回到合理的原控件；Toast、后台保存和列表刷新不得主动抢焦点。
- 编辑器保留原生文本选择、复制粘贴、撤销重做和输入法组合过程。触控手势、列表勾选、链接与附件操作不得抢走文字选区。
- 纯文本是派生数据，富文本是主数据；UI 密度、窗口大小或外观改变不得改变持久化内容。输入与保存回归优先于视觉微调。

依据：[Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)；编辑约束见 AGENTS 和 DESIGN。

## 9. 动效、滚动与直接操纵

- 每段动效应说明状态变化、空间关系或操作反馈；不为静态页面增加入场仪式。正文输入、插入点和选区即时响应。
- 拖动跟随输入，取消、反向或重新拖动能够打断过渡；手势起点不跳变，结束反馈应与最终动作一致。
- 优先系统滚动、弹性、减速与过渡，不在原生行为之上再叠一套模拟。只有实际需要时设计自定义弹簧，不把某组参数视为所有控件标准。
- 动效不改变业务提交时机，不锁住交互等待播放结束；减少动态效果时仍保留必要状态反馈。
- 性能按可见体验检查：长文、连续输入、快速滚动、大列表和窗口缩放；降低帧率、整页重建或列表跳位不能靠动画掩盖。

### 9.1 响应时机与手势判定

- 按下立即显示按下状态；按原生约定在释放或手势完成时提交。允许移出热区取消，返回热区后的行为保持平台一致。
- 交互全程连续反馈，不只在结束后播放动画；审查输入路径上的防抖、延时、任务调度与繁重布局，避免人为拖慢。
- 保留抓取点相对物体的偏移，不把物体中心瞬移到指针。离开初始可见范围时，合法拖动仍应连续；取消或窗口失焦要可靠结束。
- 点击、拖动、滚动、长按和选字可能竞争。使用原生识别器的阈值、优先级和取消关系，方向明确后再接管；不能把固定 10 px 当作跨设备标准。
- 只在确实需要双击语义时增加双击判定，不为等候第二次点击延迟普通反馈。编辑器已有双击选词等行为应保留。

### 9.2 可打断、速度衔接与弹簧

- 重定向动画从当前屏幕呈现值继续，不从旧目标或初始模型值重新开始；反向时保留合理速度连续性，避免位置或速度突变。
- 手势释放后的动画承接释放速度；二维位移按各轴的速度处理，不用一个距离值抹掉方向。优先原生手势预测与动画 API。
- 检查所用 API 的速度单位。绝对速度通常为 pt/s；若接口要求归一化速度，可按每轴 `v / (target - current)` 换算。剩余距离接近零时必须走安全分支，不能除零或注入异常巨大速度。
- 阻尼控制振荡，响应参数影响反应速度，均不等于固定播放时长。自定义原型可从无回弹、阻尼比约 1、响应约 0.3–0.4 s 开始；有明确动量时再尝试较低阻尼。它们是调参起点，不是 Apple 全局规范，也不强制替换系统默认。
- 不要求所有动画都是弹簧。淡入、状态颜色变化可以用适当过渡；可抓取、可反向的运动必须保持可打断。不同 API 的同名 duration / damping 参数不能直接互抄。

### 9.3 惯性、目标预测与越界

- 滑动吸附的目标应结合当前位置、速度和可达目标，不只选择松手位置最近的点；反向速度是用户改变意图的信号，也不能忽略位置和可达性只看速度符号。
- 需要自定义模拟时，可用指数衰减模型理解预测：每毫秒速度乘以 d（0 < d < 1），初始速度为 v pt/s，则后续离散位移近似 `(v / 1000) * d / (1 - d)`。d≈0.998 只是模型示例；单位、采样约定与目标 API 必须一致，不覆盖原生滚动减速。
- 边界外的反馈应逐渐增加阻力而非突然冻结。自定义原型可参考 `b(x) = sign(x) * L * c * abs(x) / (L + c * abs(x))`，其中 L 为正的有效范围、c 为正的阻力系数；最终必须回到合法范围。
- 越界形变只是呈现反馈，不能改变真实内容、存储值或文本选区；释放、取消和窗口变化都要有确定落点。已有系统橡皮筋效果不得重复叠加。

### 9.4 空间关系与逐帧质量

- 临时界面尽量从触发控件或关联内容处出现，进入和退出保持可理解的空间路径；可逆过渡保持方向一致。平台原生呈现优先，不强制数学上镜像所有 easing。
- 中间运动方向应提示目标与层级变化；不得把切换、完成和取消做成无法区分的动画。
- 流畅不仅是平均帧率。检查速度连续性、丢帧、布局抖动、离散跳跃和快速反向，必要时逐帧回放。
- 自定义逐帧绘制使用平台显示刷新机制，减少每帧布局和重绘，不用固定计时器模拟刷新率。模糊和伸缩可用于特定物体的运动提示，不用于正文、插入点或选区，也不是所有快速动画必需。
- 减少动态效果时优先静态状态或短淡入淡出，避免大范围位移、视差、弹跳、循环背景与突兀亮度变化；降级后仍需知道发生了什么。不要为了减轻运动而把正文临时变透明。

### 9.5 声音、触觉与视觉反馈

- 反馈与具体事件有清楚因果关系，完成、选中或碰到边界各有对应含义；动画、声音与触觉在感知上同步，不能延迟播放成另一次事件。
- 只在有价值的关键交互使用声音和触觉，不给每次输入或普通导航加效果；检查设备能力、系统偏好与用户环境。
- 系统控件自带反馈优先。没有触觉硬件、静音或辅助功能开启时仍有可理解的视觉或可访问反馈；不得把某一种感官通道作为唯一依据。

依据：[Motion](https://developer.apple.com/design/human-interface-guidelines/motion)、[Designing Fluid Interfaces](https://developer.apple.com/videos/play/wwdc2018/803/)、[Designing Audio-Haptic Experiences](https://developer.apple.com/videos/play/wwdc2019/810/)。模型与调参示例仅用于解释自定义交互，不是系统行为的稳定契约。

## 10. 模态、空态、状态与错误恢复

- sheet 用于边界清楚的临时任务，popover 用于就近选项，alert 用于必须立即处理的情况。先选择中断程度，再决定视觉样式。
- 模态有明确任务名、完成/取消或关闭路径；取消不应悄悄提交，关闭可能丢失输入时提供明确处理。避免层层模态堆叠。
- 分开设计初次空态、无结果、加载中、加载失败、保存失败、部分成功和不可用状态；不能用“暂无内容”掩盖读盘失败。
- 已确认的可撤销编辑提供撤销；不可逆的数据损失在动作前说明。普通点击、导航和可逆调整不滥用确认框。
- 提示说明发生了什么、内容是否保留、下一步如何处理。持久保存问题使用持久可恢复反馈；短暂操作提示不抢焦点，也不替代保存状态。
- 不为成功操作不断弹 Toast；进度未知不要伪造百分比。离线或同步状态仅在实际有该能力时呈现，不能把未来功能伪装为现状。

依据：[Modality](https://developer.apple.com/design/human-interface-guidelines/modality)、[Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)、[Writing](https://developer.apple.com/design/human-interface-guidelines/writing)。

## 11. 无障碍、本地化与内容包容性

- 每个可操作元素有正确角色、名称、值和状态，阅读顺序符合视觉关系；组合元素不要重复朗读装饰，也不要合并掉必要动作。
- 信息不能只靠颜色、声音、振动或动画传递。VoiceOver、键盘、触控和指针都应有对应路径，禁用原因需要可理解。
- 检查 Dynamic Type / 辅助字号、增加对比度、减少透明度和减少动态效果；这些是独立设置，不能用某一个设置代替全部。
- 常规正文以至少 4.5:1 对比度作为项目核查目标，特殊文字/图形按适用标准和实际背景评估；使用测量证据，不宣称语义色天然合规。
- 文案简短具体，日期、数字和复数按 locale 格式化；允许翻译增长与 RTL 排列。代码、数字、符号或具有固定语义方向的图标不盲目镜像。
- 不用缩小字体、裁掉按钮文字或隐藏错误信息来通过窄屏检查。不可避免的截断需提供完整内容的访问路径。

依据：[Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)、[Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)、[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)。

## 12. 走查与交付门槛

先用可交互的原型或实际 App 验证视觉与操作的整体关系，不把动效留到静态页面“完成”后才考虑。涉及新交互或重要产品取舍时，邀请实际使用者按真实任务操作，观察理解、误触、发现路径和完成过程；开发者走查与用户测试分别记录。必要时慢速或逐帧回放动效，正常速度再确认手感。没有用户参与不能声称完成用户测试。

每次只选择改动影响的场景；以下是覆盖维度，不要求每次小修复全量重跑。

| 维度 | 必要观察 | 不能替代它的证据 |
| --- | --- | --- |
| 几何 | 实际窗口中的累积边距、文字基线、圆角、描边、热区 | 只有设计稿或代码常量 |
| 同心圆角 | 直边与转角留白、窗口状态变化、底部状态条 | 仅调用 `.concentric` |
| 自适应 | 最小/常用/宽窗口，长内容、字号变化、键盘出现 | 单一尺寸截图 |
| 状态 | 选中、按下、禁用、失焦、空态和失败 | 正常状态截图 |
| 操作 | 输入、选区、撤销、切换、返回与保存恢复 | 构建通过 |
| 输入方式 | 指针完整热区、触控、键盘与 VoiceOver | 辅助功能设置值代替鼠标拖动 |
| 外观 | 浅深色、增加对比度、减少透明度/动态效果 | 语义 API 存在 |
| 连续交互 | 抓取偏移、快速反向、速度交接、越界、取消、失焦与手势竞争 | 单次完整播放动画 |
| 多感官 | 反馈因果与同步、静音/无触觉硬件下的可理解性 | 只看到动画 |
| 用户理解 | 真实任务中的发现路径、误触、完成与恢复 | 开发者自测 |

问题记录包含场景、实际表现、预期、影响与证据；优先级按数据损失 → 输入/访问阻断 → 状态错误 → 几何精修。不能只报告“通过”。执行细节见 [验证](../../docs/verification.md)。

新增规则注明是官方依据、用户决定还是项目取舍；产品尺寸改动同步 DESIGN。实际 UI 未验证或平台未覆盖时明确写“待验证”。本文不授权新增功能，也不把规则落盘当作 App 已达标。
